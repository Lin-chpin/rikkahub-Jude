# AI 语音条长上下文故障经验

## 现象

普通聊天中，模型成功调用 `text_to_speech`，工具卡片显示执行成功，但最终没有语音条，也没有错误提示。新窗口较少出现，长上下文会明显增加概率。未配置 TTS Provider 和已配置 TTS Provider 都可能出现。

## 日志证据

典型排查记录如下：

```text
newExecutedVoiceToolMessages=1
assistantCandidatesAfterTool=1
markerCandidatesAfterTool=0
parseableCandidatesAfterTool=0
matchedReplyMessageId=none
```

这表示本轮工具确实执行完成，工具后也有 assistant 回复，但回复没有输出 `【语音条】`，因此没有进入 TTS Provider 配置和合成阶段。`voiceToolErrors=none` 只表示没有识别到工具错误，不代表结构化续写成功。

## 根因

`text_to_speech` 是一次性的模式切换工具，本身没有文本参数。工具返回格式协议后，模型需要继续输出带 `【语音条】` / `【文本】` 标记的完整回复。长上下文会增加模型遗忘这条局部协议的概率。

物化器原先在找不到结构化目标时直接返回，导致工具 UI 看起来成功，但语音生成链路静默结束。TTS 是否配置并不是这个分支的根因，因为目标匹配发生在 Provider 配置检查之前。

另一个容易遗漏的边界是工具调用和最终 assistant 回复可能落在不同消息节点。错误必须写回触发本轮物化的工具消息节点，不能只更新最终 assistant 回复，否则工具卡仍会显示执行成功。

## 修复原则

- 工具结果提示词增加协议锁，明确下一条 assistant 回复必须包含至少一个 `【语音条】`。
- 如果工具已执行且模型输出了普通 assistant 回复，客户端将该回复规范化为单段语音，继续走 Provider 配置、TTS 合成和音频保存流程。
- 如果工具已执行但工具后没有可用 assistant 正文，客户端给工具卡写入 `TOOL_FAILURE`，不再静默跳过。
- 结构化回复仍优先于兜底回复，正常的混排、多语音段和音频分段逻辑不变。

## 后续诊断

`voice_reply.materialize.target` 阶段用于区分本轮工具、assistant 候选、协议标记和最终匹配目标。使用兜底时会显示 `usedProtocolFallback=true`，便于判断模型是否再次遗漏协议。
